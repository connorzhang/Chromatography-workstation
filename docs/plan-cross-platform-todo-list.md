# 跨平台边缘节点 (Go) 开发 TODO 计划与差异分析

基于对遗留 C# 色谱工作站项目（`IBrainChrom2018`）的全面代码检索与功能分析，现将旧系统中的所有功能模块与新重构的 Go 边缘节点（`src/edge/`）目前已实现的功能进行对比，并整理出后续开发的 TODO 计划。

## 1. 核心状态评估

- **当前 Go 项目定位**：目前 `edge` 节点主要作为**轻量级数据采集与简单在线分析网关**。已经跑通了底层 TCP 通讯、基础 Modbus/MQTT 上报、前端实时波形展示以及“非甲烷总烃”的基础计算逻辑。
- **与 C# 的差距**：C# 版本是一个功能大而全的实验室级别色谱工作站 (CDS)，包含了复杂的多阶程序升温、自动校准、富文本报表以及合规审计追踪。

## 3. 开发优先级建议

针对在线监测场景的**近期核心目标**，建议的开发优先级如下：

1. **P1 (核心阻碍 - 必须优先解决)**
   - [x] **定义底层核心数据结构**: (如 `Peak`, `Compound`, `Level`, `Method`)，确保与遗留系统完全向后兼容 (已完成 `schema.go` 映射)。
   - [x] **实现底层持久化**: 在 Go 后端 (`persist_file.go`) 落地存储机制。
   - [x] **实现 RESTful API 契约**: (如 `GET /api/method`, `POST /api/control/*`)。
   - [x] **实现硬件反控指令翻译**: (如 `tempToBCD2` 将参数封装成 Cmd 8 报文下发)。
   - [x] **实现校准与浓度计算**: 在 `analyzer.go` 中加入基于多点校准的 `calcConcentration`。
   - [x] **完善分析内核**：实现了基于老系统滑动平均的数据平滑、多模式基线切割(ForwHorz/BackHorz/General)以及支持峰分组(Peak Grouping)如非甲的扣减逻辑。

2. **P2 (业务刚需 - 紧随其后)**
    - [x] **重构前端界面结构**: 使用纯原生 HTML/JS 搭建 SPA 单页应用，包含“大屏”、“谱图”、“方法”、“设置”等核心选项卡。
    - [x] **前端动态数据接入**: 连通前端界面与后端的 RESTful API（方法列表动态加载、控温下发按钮）。
    - [x] **完善历史报表**: 引入 `modernc.org/sqlite`，实现本地 SQLite 数据库的历史结果检索，并支持导出 CSV 报表。
    - [x] **完善 Modbus 从站与标识**: 启动 Modbus/TCP 1502 监听，增加寄存器 800 起 12 个寄存器存放 24 位 ASCII 设备标识，并在每次计算结果后自动更新 100/102/104 浓度寄存器。
    - [ ] **Canvas 波形渲染**: 将实时采集到的高频数据点流（WebSocket/SSE）呈现在前端 Canvas 图表中。
    - [ ] **支持多位阀切换与外部事件表**: 后端处理 Cmd 10 报文与对应的前端设置交互 (已占位，待精准时序)。
    - [ ] **MQTT 遥测上云**: 引入 Paho MQTT Go，将历史结果格式化后推送到 Elasticsearch 溯源。

3. **P3 (完善体验 - 后期迭代)**
   - **前端集成**：基于原生 JS 对接已完成的后端 API，实现截图中的仪表盘和控制交互。
   - **报表导出**：PDF 生成或打印功能。
   - **审计日志**：操作记录留痕。

## 4. 高级项目管理与文档同步规范 (过程裁剪)

为了保证项目的可持续迭代，并在每个里程碑后能够进行有效的**项目复盘 (Retrospective)**，我们将采用裁剪后的高级项目管理流程，确保核心过程文档与代码同步输出：

### 4.1 必需的过程文档清单 (存放于 `docs/` 目录)
1. **API 接口契约文档 (`API_DESIGN.md`)**：
   - 在开发任何后端逻辑前，优先输出前后端交互的 RESTful API 和 SSE 数据结构规范。
2. **核心数据结构设计 (`DATA_SCHEMA.md`)**：
   - 记录存储于 SQLite 或 JSON 中的核心模型，如 `Method` (分析方法)、`Calibration` (校准曲线)、`Result` (分析结果) 的实体关系。
3. **测试报告与复盘记录 (`SPRINT_RETROSPECTIVE.md`)**：
   - 记录每个 P1/P2 阶段完成后的测试通过情况、硬件联调问题（如通讯延时、死锁）以及解决方案，供后续避坑复盘。

### 4.2 开发工作流
1. **文档先行**：确定要开发的功能模块（如校准曲线） -> 输出 `API_DESIGN.md` 与 `DATA_SCHEMA.md` 的对应章节。
2. **后端主导开发**：Go 后端实现逻辑 -> 编写简单的 Shell 或 HTTP 脚本验证（不依赖前端）。
3. **前端对齐**：原生前端依据契约文档接入接口。
4. **测试与复盘**：完成集成测试 -> 记录问题与解决方案到 `SPRINT_RETROSPECTIVE.md`。
